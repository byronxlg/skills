# Design work: a positive idea, a written plan, prototypes, a blind juror

Any UI, page or screen work starts from a design idea, never from a defect list. Plan first, then build, in this order:

- Ground the look in a published design system Byron has picked for the product (ask once, in plain words, if none is picked) and map each element to a named pattern in it, taking its behaviour (feedback, progress, states) and writing rules, not only its sizes and colours. Do not decide on taste; if a wanted element has no pattern, say so and ask. Only where he asks for a distinctive look with no system: load the `taste` skill (app screens: `references/app-screens.md`) and write 5+ patterns borrowed from named good products, each with what it changes on screen.
- Before any layout, write a one-line brief per screen (who lands here and from where, what they already know, the one thing they do, what they must learn at this moment) and a state table per control (every button, row and field against rest, pressed, busy, done, failed, disabled). Every piece of text needs a home in a brief: it goes where the person needs it, never into a free slot. Every cell of the table is built and captured.
- Site-wide or "premium" asks need a design guide before any screen: palette as named roles (ground, ink, accent, meal or category colours) with contrast checked, type scale, spacing, radii, elevation, motion, and the taste `tells.md` list as banned patterns. Commit it as tokens plus a doc, and apply it to every page, not only the one in hand.
- Stateful flows (chat, checkout, multi-step) need a state map before layout: every state, every action a user can take from it (back, edit an earlier step, click a stale item, reload, error, empty), and the way forward from each. No dead ends; each row becomes a browser test.
- Get an independent review of the briefs, the state tables, the guide and the state map before prototyping; fix what it finds.
- Build two genuinely different directions as static prototypes with real data and look at every capture yourself before anyone else does. Then build one screen to finished before starting the next, and put the real thing in front of Byron early: shrunken mock-ups hide how a page feels.
- Words: a screen never explains itself in prose. Follow the picked system's writing guide (Apple's: "Check each word to be sure it needs to be there"; no "we"; possessives sparingly) and hold each screen to a word budget with a test. A budget alone makes text cryptic, so pair it with a cold read: a fresh agent with no context says what each screen is, what to do next, and what every line means; anything it cannot explain fails.
- Test in the engine the audience uses (Safari for anything opened on a phone); a missing engine is a blocker to fix, not a footnote. The walk-through presses, holds, slows the network, submits twice and goes back, and captures those moments. Stills of pages at rest with motion off prove layout only.
- Judge with a blind juror: a fresh agent sees the before and the candidates unlabelled, against named reference products, and walks the state map; ship the winner only if it beats the before, after fixing the juror's top defects. Subtraction is not a design pass: removing boxes or merging text styles must come with added hierarchy (size and weight contrast, grouping by region, a focal point). A screen is done when its captures say so, at rest and mid-action, in the audience's browser, for every page the change touches: never from tests or code review alone, and never with a caveat ("not checked in Safari" means not done).
- Why: ptt, 2026-11-02. Three subtractive passes left a wall of same-weight grey text; then the site had no shared palette and the chat had dead ends nobody had mapped. judge, 2026-11-18. Nine pages built in one pass and checked only as still Chrome screenshots: buttons gave no feedback on an iPhone, a disclosure sat as fine print under a button because that slot was free, and every screen explained itself in prose until Byron said so.
